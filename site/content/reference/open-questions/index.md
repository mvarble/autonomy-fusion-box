Everything here is unverified until the **Status** column says otherwise. A datasheet
can close a question about what a part is specified to do. Only a measurement can close
a question about what this hardware does.

Status values:

- **OPEN**: no usable answer yet.
- **DOC**: documented by the vendor, not yet measured on this hardware.
- **MEASURED**: confirmed on this hardware; link the probe or milestone measurements that did it.
- **DECIDED**: not a fact but a choice, settled by an archive entry; link it.

Each "How we close it" ends with the size of the job:

- **Quick**: a short probe, one reading.
- **Write-up**: a fuller probe, with a method worth recording.
- **Inside M*n***: closed by that milestone's own build or measurements, because it needs the
  box's code or is one of the milestone's numbers.

Source tags such as `[IM]` are defined in [Sources](#sources). Last reviewed 2026-11-13.
One item has been measured: #1, the firmware version.

| 10  | How does `ESF-RAW.sTtag` map to GNSS time?                                                       | OPEN, **highest risk** | `[ID §3.11.4]` defines `sTtag` only as "sensor time tag", with no unit or epoch. `ESF-RAW` has no `iTOW`. `[IM §3.2.5.2]` gives a 1 ms time tag resolution and `CFG-SFCORE-SEN_TTAG_*`, but in the context of `ESF-MEAS`. `ESF-MEAS.calibTtag` is not usable: `calibTtagValid` is always zero `[ID §3.11.3]`. **The manuals do not give a mapping.** Observed: `sTtag` wraps at 2²⁴ although the field is typed U4 ([rtk-inspection](../../archive/rtk-inspection/measure.md)). | (a) Tick rate: `sTtag` deltas against sample count, then long-run against `iTOW` over hours. (b) Wrap value: log through a wrap or read `SEN_TTAG_MAX`. (c) Offset: a shared physical event, such as a Pico-timed solenoid or tap seen in the accelerometer, with the AD3 on the actuator. (d) Ask u-blox support. Do not write a tick rate down from memory. **Write-up:** a fuller probe for (a) and (b); (c) needs the Pico, so it closes inside a milestone. |

The tick unit is not documented for `ESF-RAW`, so the rate in Hz is still open.    | The framing is closed. ## OS decision evidence

Raspberry Pi OS is Tier 3 for Jazzy, and the ROS docs suggest either Ubuntu 24.04 directly
or Ubuntu containers on Pi OS `[ROS-PI]`. RoboStack is a third route, outside those tiers
`[ROBOSTACK]`, and the one the box takes. The argument is in the
[foundations writeup](../../archive/foundations/writeup.md).

| Concern                      | Ubuntu 24.04 + native ROS 2                                                                                                                  | Pi OS + ROS 2 in Docker                                        | Pi OS + ROS 2 from Pixi                                                                                        |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| ROS 2 support                | Tier 1 arm64                                                                                                                                 | Tier 1 inside the container, Tier 3 on the host                | Community-built `[ROBOSTACK]`, no ROS support tier                                                             |
| Innomaker trigger and strobe | Not mentioned by the vendor                                                                                                                  | Documented on Pi 5 for Bookworm and Trixie `[INNO-GH]`         | The same                                                                                                       |
| `imx296.trigger_mode`        | **Unverified** on the Ubuntu kernel                                                                                                          | Present in `rpi-6.12.y` `[IMX296-C]`                           | The same                                                                                                       |
| `pps-rp1` overlay with echo  | Needs Pi kernel `1:6.12.70-1+rpt1` or later `[SATPULSE]`. The noble listing suggests a 6.8 base `[UBU-PKG]`. **Unverified on a real image.** | Available at that kernel version or later                      | The same                                                                                                       |
| libcamera for Pi 5           | Build the `raspberrypi` fork from source in the workspace `[CAMERA-ROS]`                                                                     | Same build, inside the image                                   | Prebuilt `rpi_fork` `[CF-LIBCAMERA]`; see #30                                                                  |
| Device access                | Direct                                                                                                                                       | Pass through media, video, subdev, DMA heap and serial devices | Direct                                                                                                         |
| Time sync                    | Host                                                                                                                                         | Host                                                           | Host. Under every option the same host process owns the F9R port, so the coarse-time feed never depends on ROS |

On the Pi, whichever way ROS 2 is installed, check these on the real image first:

```sh
uname -r
getconf PAGESIZE
ls /boot/firmware/overlays/pps-rp1.dtbo /boot/firmware/overlays/pps-gpio.dtbo
modinfo imx296 | grep -i trigger
cat /sys/bus/pci/devices/0002:01:00.0/link/l1_aspm
```
